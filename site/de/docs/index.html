Status & Roadmap

Sharemee ist in früher Entwicklung. Das Fundament steht: die Coworkee-Kernpakete und eine Sharemee-Aspire-Anwendung mit Datenbank, Migrationen und API. Die Funktionen folgen in Phasen.

PhaseUmfang
P0Fundament: Module, Dispatcher, Audit, Outbox, Auth-Server, User, Rollen, Rechte, Einstellungen, Mail-Vorlagen, Themes, Echtzeit, Setup-Wizard
P1Graph, Metadaten und Assets: Ordner, eigene Typen, Uploads, Versionen, Renditions, Dateianzeige, Rechte pro Element
P2Suche mit Facetten, gespeicherte Suchen, Reindex
P3Vollständige Rendition-Pipeline: Video, Office, PDF, 3D, Wasserzeichen, Zuschnitt, Archive, Zip-Downloads

P7Knowledge Base und Intranet
P8KI-Assistent und MCP-Tools
P9Datenmigration und öffentliche Pakete

Voraussetzungen

  • .NET SDK 10.0.300 oder neuer (festgelegt in global.json)
  • Docker für die Aspire-Container und die Integrationstests
  • Das Coworkee-Repository neben Sharemee als ../coworkee, bis die Pakete veröffentlicht sind

Schnellstart

pwsh ../coworkee/build/pack-local.ps1
dotnet run --project src/Shareme.AppHost

Das Skript packt Coworkee nach ../coworkee/artifacts/nuget, einen lokalen Feed, den nuget.config bereits kennt. Der AppHost startet Postgres, Redis und Mailpit, führt die Migrationen einmal aus und startet dann die API. Swagger liegt unter /swagger der API.

Paket- oder Projektreferenzen

Projekte geben an, was sie brauchen, mit <CoworkeePackage Include="Coworkee.Application" />. Standardmäßig werden daraus NuGet-Paketreferenzen auf den lokalen Feed. Um in Coworkee zu debuggen oder es ohne neues Packen zu ändern, auf Projektreferenzen umschalten:

dotnet build -p:CoworkeeReferenceMode=Project

Module

Jede Bibliothek und jede Funktion ist ein Modul. Ein Modul registriert seine Dienste und nennt die Module, von denen es abhängt; der Loader ordnet sie so, dass Abhängigkeiten zuerst laufen, und erkennt Zyklen.

[DependsOn(typeof(CoworkeeApplicationModule))]
public sealed class ShareMeApplicationModule : CoworkeeModule
{
    public override void ConfigureServices(ModuleServiceContext context) =>
        context.Services.AddMessagingFromAssembly(typeof(ShareMeApplicationModule).Assembly);
}

Ein Web-Host registriert ein Root-Modul mit builder.AddCoworkee<TRoot>() und ruft app.UseCoworkee() auf. Module, die Endpunkte mappen, implementieren IWebModule.

Commands und Queries

Use Cases sind Requests, die genau ein Handler bearbeitet. Der Dispatcher legt um jeden Request eine feste Middleware-Pipeline: erst Logging, dann Validierung, dann die Unit of Work, die Änderungen nur bei erfolgreichen Commands speichert. Autorisierung bekommt ihren reservierten Platz in der Pipeline mit Phase P0.

public sealed record GetSystemInfo : IQuery<Result<SystemInfo>>;

internal sealed class GetSystemInfoHandler : IHandler<GetSystemInfo, Result<SystemInfo>>
{
    public Task<Result<SystemInfo>> HandleAsync(GetSystemInfo request, CancellationToken ct) =>
        Task.FromResult<Result<SystemInfo>>(new SystemInfo("Sharemee", "0.1.0"));
}

FluentValidation-Validatoren in derselben Assembly werden automatisch gefunden. Schlägt die Validierung fehl, kommt ein Validierungsfehler zurück, ohne dass der Handler läuft.

Persistenz-Konventionen

Den Datenbankkontext von CoworkeeDbContext ableiten und mit AddCoworkeeDbContext<T>() registrieren. Marker-Interfaces an Entitäten schalten Verhalten ein:

MarkerWirkung
IAuditableErstell- und Änderungszeit und -User werden beim Speichern gesetzt
ISoftDeleteLöschen setzt ein Flag; gelöschte Zeilen sind in Abfragen ausgeblendet
IMultiTenantMandant kommt vom aktuellen User; Zeilen anderer Mandanten sind unsichtbar und nicht beschreibbar
IHasConcurrencyTokenOptimistische Nebenläufigkeit; Konflikte erscheinen als HTTP 409

Jedes Einfügen, Ändern und Löschen schreibt einen Audit-Eintrag mit altem und neuem Wert je Feld, auch für Änderungen in JSON-gemappten Unterobjekten. Mit [Sensitive] werden Werte maskiert, mit [NotAudited] ausgelassen.

Domain-Events und Outbox

Aggregate lösen Domain-Events aus. Beim Speichern landen sie in derselben Transaktion in einer Outbox-Tabelle. Ein Hintergrundprozess liefert sie an IDomainEventHandler<T>-Implementierungen aus, und zwar als der User und Mandant, die sie ausgelöst haben, wiederholt Fehler mit exponentiellem Backoff und gibt nach fünf Versuchen auf. Handler sollten idempotent sein: Die Zustellung erfolgt mindestens einmal.

HTTP-Ergebnisse

group.MapGet("/info", (IDispatcher dispatcher, CancellationToken ct) =>
    dispatcher.SendAsync(new GetSystemInfo(), ct).ToHttpResult());

Erfolge liefern 200 oder 204. Fehler werden zu Problem Details: Validierung 400, verboten 403, nicht gefunden 404, Konflikt 409, alles andere 500. Jedes Problem trägt den Fehler-code.

Tests

dotnet test --solution Shareme.slnx

Die Tests nutzen xUnit v3 auf Microsoft.Testing.Platform. Integrationstests laufen gegen ein echtes Postgres im Container und setzen es zwischen den Tests zurück. Der AppHost-Smoke-Test startet die ganze Aspire-Anwendung und ruft die API auf.
