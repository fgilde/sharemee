# P0.3d Account flows, setup steps, admin extras – Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans (native). Tests per case are written first.

**Goal:** Passwort vergessen/zurücksetzen, E-Mail-Bestätigung, Selbstregistrierung (wenn erlaubt, Freigabe durch Admin), 2FA mit Authenticator-App und Wiederherstellungscodes, Admin kann Reset-Mail senden und effektive Rechte sehen, Setup-Wizard mit System-Check und Mail-Schritt.

**Architecture:** Neues Paket `Coworkee.Account` (DependsOn Identity + Mailing): `IAccountMailer` (Reset- und Bestätigungslinks mit `UserManager`-Tokens, Basis-URL `Coworkee:Account:PublicAuthUrl`), Setting `Account.AllowRegistration`, Admin-Endpunkt `POST /api/v1/identity/users/{id}/password-reset`. `Coworkee.AuthServer` (DependsOn Account) bekommt Razor-Seiten `ForgotPassword`, `ResetPassword`, `ConfirmEmail`, `Register`, `LoginWith2fa`, `Manage/TwoFactor`. Identity bekommt `GET /api/v1/identity/users/{id}/permissions` (effektiv) und Setup-Erweiterungspunkte in `Coworkee.Application.Setup`: `ISetupStep` (läuft in der Setup-UoW) und `ISetupCheck` (`GET /api/v1/setup/checks`, nur vor dem Setup). Settings liefert den Schritt „Settings aus dem Setup-Request“, Mailing den SMTP-Check. Der Wizard bekommt die Schritte System-Check und Mail.

**Spec:** `docs/superpowers/specs/2026-10-01-p0-foundation-design.md` 3.4, 3.6, 3.7.

## Rulings

- Client Credentials verschoben nach P4 (Integrationen): ohne Rechtemodell für Clients ohne Nutzen.
- Tenant-Verwaltung verschoben, bis mehr als ein Tenant erlaubt ist.
- Branding-Schritt im Wizard verschoben: Theme ist nach dem Setup unter Themes wählbar; Default ist Coworkee.
- Freigabe-Mail `Identity.RegistrationApproved` beim Aktivieren verschoben (braucht ein Ereignis aus Identity, das Mailing auslöst).
- Externe Provider und Passkeys bleiben wie in der Spec nach P1.

## Review Focus

1. Passwort-vergessen verrät nicht, ob eine Adresse existiert (gleiche Antwort, keine Mail für inaktive User).
2. Reset-/Bestätigungstoken sind einmalig und an den User gebunden; fremde userId mit gültigem Token schlägt fehl.
3. 2FA aktivieren verlangt einen gültigen Code; Login mit aktivierter 2FA ohne Code erreicht nie einen OIDC-Code; Recovery-Code ist einmalig.
4. Registrierung bei deaktiviertem Setting ⇒ 404; registrierter User bleibt inaktiv bis zur Freigabe.
5. Setup-Schritt mit ungültigem Setting ⇒ ganzer Setup-Vorgang abgelehnt, nichts angelegt.
